문서의 목적. M2에서 주문 데이터를 한 테이블에서 이벤트 기록으로 바꾸는 설계를 설명하고, 구현에 들어가기 전에 방식과 완료 기준의 승인을 받는다.

1요약

지금 주문 상태는 한 행을 덮어써서 바뀌므로, 언제 누가 무엇을 바꿨는지 남지 않는다[D1]. 이 마일스톤은 상태 변경을 이벤트로 쌓고 현재 상태는 이벤트에서 계산한다.

  • 바꾸는 것. 주문 테이블의 상태 열 대신 이벤트 테이블에 변경을 추가만 한다.
  • 지키는 것. 기존 API 응답은 그대로이며, 조회 지연 p95 50 ms 이하를 유지한다.

2배경과 목표

M1 결과 보고서에서 주문 분쟁 12건 중 9건이 변경 이력 부재로 원인을 확인하지 못했다[D2]. 이벤트 기록은 이력 보존의 표준 방식이다[R1].

표 1. 지금의 문제와 대응. [D1, D2]

문제근거대응
이력 없음분쟁 12건 중 9건 원인 미상이벤트 테이블(3.1절)

6위험과 대응

결과 보고서에서는 시도마다 아래 상자를 쓴다(견본).

① 버전 번호로 충돌 거부 (M2.2) — 채택

이유. 동시 수정 시 마지막 쓰기만 남아 월 3~5건의 변경이 사라졌다[D1].

방식. 이벤트마다 직전 버전을 함께 보내고, 다르면 거부한다(낙관적 동시성 제어)[R2].

결과. 동시 수정 시험 1,000회에서 유실 0건, 거부 후 재시도 성공 100%.
